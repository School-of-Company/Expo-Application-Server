# Expo Application Server

Single-module Application service built with Kotlin 2.3.21, Spring Boot 4.1.1, Java 21, and Gradle. PostgreSQL with Flyway stores program applications. Local development also starts Redis.

## Where to work

- Kotlin source lives in `src/main/kotlin/team/startup/application`. The feature is `domain/application`; shared internal-token security is in `global/security`.
- Within the feature, use `presentation` for HTTP controllers and request/response DTOs, `service` for one public API operation per service interface, `service/impl` for its single-purpose `*ServiceImpl`, `repository` for JPA, and `entity` for persisted models. Controllers inject the operation interfaces and delegate to them.
- Every API operation has one service interface declaring only `execute(...)` and one matching `*ServiceImpl` overriding it. Controllers delegate each API operation to its interface. `RegistrationWorkflow` is shared registration logic behind the four public registration services; `RegistrationGateway` handles outgoing calls.
- Use constructor injection. Put database transaction boundaries on the public operation methods in the implementations: `@Transactional(readOnly = true)` for reads and `@Transactional` for writes. Registration makes remote calls and has no local database transaction.
- Use explicit `@field:` targets for Jakarta validation on request DTO properties and `@field:Valid` for nested DTOs. Validate request bodies with `@Valid` in controllers. Keep path IDs as scalar parameters.

## Contracts to preserve

- Internal program application APIs live under `/internal/standard-program-applications`, `/internal/training-program-applications`, and `/internal/program-applications`. Keep their paths, application ID fields, status codes, and list order. Standard and training application lists contain no attendance fields; Attendance owns program attendance times. The standard and training application controllers own request validation and HTTP response statuses.
- Standard and training apply/delete and training replace use PostgreSQL transaction-scoped advisory locks. Preserve trainee-before-sorted-program locking, deleted-program markers, duplicate/capacity checks, atomic writes, retry behavior, and concurrent delete behavior. `ProgramApplicationConflictException` returns 409.
- `/internal/**` requires `X-Internal-Token` matching `APPLICATION_INTERNAL_TOKEN`; the value must be configured at startup. `InternalSecurityConfig` permits health and GET Prometheus without that token. GET `/application/expos/{expoId}/preregister-sessions/{sessionId}/capacity` is public independently of registration POST enablement and uses the required ledger query service. The four public `/application/**` registration POST routes are available only when `APPLICATION_REGISTRATION_ENABLED=true`.
- 관리자 그룹 발송 공개 프록시 계약과 대표자 번호, 대상 fingerprint 규칙은 `docs/admin-group-messaging.md`에 있다. 이 경로는 전달받은 Bearer JWT를 Expo 관리자 권한 공급자에 매번 검증한 뒤 User 대표 참가자와 Notification 내부 API를 호출한다.

Preserve the optional `Idempotency-Key`, pre/field form rules, form-question snapshot, response/error mapping, and standard-participant count update. `RegistrationHttpTests` covers the integration contract.

- 하위 서비스 HTTP 호출은 `DownstreamCircuits.send`를 거친다. 서비스(expo/user/form/attendance/notification)별 Resilience4j 차단기(최근 20회 중 10회 이상·50% 실패 시 10초 open)이며, 타임아웃·연결 실패·5xx만 장애로 세고 4xx와 본문 해석 오류는 세지 않는다. 재시도는 GET의 즉시 연결 실패에 75ms 뒤 1회뿐이고 쓰기와 타임아웃은 재시도하지 않는다. 사용자 요청 한 건은 회로에 한 건으로 세며, 재시도 앞의 실패는 세지 않는다. 회로가 열리면 `IOException`으로 실패해 각 게이트웨이의 기존 연결 실패 오류(503)로 바뀐다. 새 게이트웨이는 `HttpClient.send`를 직접 부르지 말고 이를 쓴다. `DownstreamCircuitsTests`와 빈 공유를 확인하는 `DownstreamCircuitsWiringTests`가 다룬다.
- Outgoing internal calls use only per-target tokens: `APPLICATION_REGISTRATION_{EXPO,FORM,USER}_INTERNAL_TOKEN` (also used by admin, cancellation and capacity gateways) and `APPLICATION_ADMIN_GROUP_MESSAGE_{EXPO,USER,NOTIFICATION}_INTERNAL_TOKEN`. Never fall back to `APPLICATION_INTERNAL_TOKEN`. Startup fails when registration is enabled without its Expo/Form/User tokens, or when an admin group messaging URL is set without its token; disabled features still start. `OutboundInternalTokenConfigTests` covers this.
- General preregistration requires `sessionId` and enabled Attendance delivery. Accept the whole party (maximum five) into confirmed seats, queue the whole party as WAITING, or reject before User saving (#99, `docs/preregistration-waitlist-design.md`). Commit the reservation and original User/form snapshot first; use its fixed User requestId on every recovery. Timeouts, malformed success responses and uncertain failures retain seats. Confirmed applications and Attendance/count outboxes commit together. Field and trainee registration retain their existing flow, except that a STANDARD FIELD registration of a participant with preregistration history here (#249 cancelled, #261 also other-day confirmed) queues an Attendance `PUT .../preregister-session/field-registration` (V38) on the same per-participant outbox after the User save; its targets are the representative plus User's `fieldParticipantIds` (#275, participants this request made FIELD; a same-key retry repeats the first list, a new-key resend is empty); a User response without that field releases only the representative. When the phone's representative has a session confirmed for today (KST), STANDARD FIELD registration returns 409 `ALREADY_PREREGISTERED_TODAY` before User; otherwise the unchanged `applicationType: "FIELD"` request makes User switch the existing PRE representative to FIELD (#261); User has no extra field, so this 409 must stay before the User call.
- Attendance uses `APPLICATION_ATTENDANCE_URL` and `APPLICATION_ATTENDANCE_INTERNAL_TOKEN` matching Attendance `INTERNAL_TOKEN`. Durable PUT/DELETE delivery preserves per-participant order; remote delayed requests cannot be fenced by the current provider contract. Never fabricate a successful response when participant IDs do not match the reserved party.
- Do not modify V5 or V5_1. V6 adds Attendance outbox; V7 removes participant-level waiting/promotion and adds reservations/count retries. V7 refuses deployment with live WAITING rows; an operator must resolve them explicitly. V17 adds party-level WAITING reservations; withdrawn parties are terminal REJECTED rows, and code from before V17 must not run while WAITING rows exist.
- Preregistration waiting parties are never sent to User, so they get no QR. `APPLICATION_PREREGISTER_WAITLIST_INTAKE_ENABLED` gates only new waiting parties. Promotion is automatic strict FIFO under the Expo lock and stops after the PRE form `endDate`, while `closed`, or from `startedAt`; promoted parties reuse the RESERVED recovery path. New parties never overtake the queue. Sessions with history but no stored `waitingCapacity` accept no waiting until the internal adoption PUT.
- V8 indexes normalized reservation phone numbers. Capacity readers use a shared Expo lock; submissions use the exclusive lock and recheck capacity. Outbox HTTP uses a separate session lock per participant, without an open transaction or Expo lock. Purge queues cancellations and an in-flight PUT is followed by DELETE when the tombstone is observed. Expo purge (#211) takes optional `{standardProgramIds, trainingProgramIds}`, runs the per-program application delete (with deleted-program markers) for each ID, then deletes the expo's program session ledger, offers, guardian batches, program state and report snapshots; receipt sequences stay so numbers are never reused.
- A saved User ID mismatch or active-participant conflict retains reserved seats with `error_status` and infinite `next_attempt_at`. Internal GET `/internal/expos/{expoId}/preregister-reservations/{requestId}` exposes recovery status without form/phone data. After fixing the authoritative User result, POST the same path plus `/retry` to reuse the original User requestId and snapshot; never fabricate IDs or release ambiguous seats. Uncertain delivery failures (`retry` path) that last past `application.registration.reservation-review.max-attempts` (40) or `max-age-minutes` (60) since the retry window opened (row creation or the last operator retry) move to the same `needsReview` state with a single warning log; seats stay held (#222).

## Logging

The Expo log standard, shared by every Expo service (Spring and Nest alike) so the shared Loki in Expo-Monitoring can label them the same way:

- Every line written to stdout is one JSON object (`logback-spring.xml`, `LogstashEncoder`) with at least `@timestamp` (ISO-8601/RFC3339), `level` (uppercase `TRACE`/`DEBUG`/`INFO`/`WARN`/`ERROR`), `service` (the Eureka app name, `spring.application.name`), `module` and `message`. Other keys (MDC values, `logger_name`, `stack_trace`) may follow. Nothing else goes to stdout: the Spring banner is off and Logback status warnings must not appear.
- The log pipeline reads only these key names and has no per-service fallback. When a service's logs do not show up or the fields do not match, fix the service's log output, never add parsing fallbacks to the pipeline.
- `module` is derived from the logger name by `ModuleNameConverter`, never set at the call site: for `team.startup.application.{domain|global}.<x>...` it is `<x>`, otherwise the logger name's parent package. Nest services reuse the per-class logger context (`nestjs-pino` `renameContext: 'module'`).
- `HttpAccessLogFilter` (`global/logging`) writes one access line per request with module `HttpAccess`: `<METHOD> <path> status: <code> (<ms>ms)` (e.g. `POST /application/{expoId} status: 201 (12ms)`), where path is the matched route template or else the raw URI without query or path parameters (max 200 chars). INFO below 400, WARN for 4xx, ERROR for 5xx and client aborts (499, once). It runs outside Spring Security so 401/403 are logged, logs async/SSE requests when they complete, and skips `/actuator/**` and API docs. Never add query strings, headers, cookies or bodies to it. `LOGGING_HTTP_ACCESS_ENABLED=false` (`logging.http-access.enabled`, default true) turns it off.
- With the `local` profile the same JSON is also written to `${EXPO_LOG_DIR:-~/.expo/logs}/<service>/app.log` for the local Loki file tail. Production writes stdout only (pm2 captures it); add no log file settings there.
